docker_architecturethree flows converging at the kernel
unlike a VM — one kernel, processes with walls
control flow
Your docker run command travels down a chain of daemons. The CLI talks to dockerd over a unix socket; dockerd asks containerd to manage the lifecycle; containerd calls runc to actually spawn the process. Each step delegates further down.
image flow
Image layers are pulled from a registry, cached locally by content hash, then stacked by overlayfs into a single filesystem the container sees. Read-only image layers underneath, a writable layer on top — copy-on-write, no duplication.
runtime isolation
The container is just a process. Namespaces give it its own view of PIDs, network, filesystem, and hostname. cgroups cap its CPU, memory, and I/O. seccomp filters which syscalls it can make. No guest OS. One kernel, shared.
