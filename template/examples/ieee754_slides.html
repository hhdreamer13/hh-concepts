Computers count in binary.
Most decimals don't fit.
In decimal, you write fractions as powers of 10: 0.1 = 1/10, 0.25 = 25/100. In binary, fractions are powers of 2: 1/2, 1/4, 1/8, and so on. Most decimal fractions cannot be expressed as a finite sum of those — they repeat forever in binary, just like 1/3 repeats in decimal.
decimal — base 10
1/3 = 0.333333...
1/7 = 0.142857...
1/4 = 0.25 ✓
1/10 = 0.1 ✓
binary — base 2
1/3 = 0.010101...
1/10 = 0.000110011...
1/4 = 0.01 ✓
1/2 = 0.1 ✓
Notice: 0.1 repeats in binary. The computer has to cut it off somewhere. That cut is the source of everything that follows.

IEEE 754 — where the cut happens.
IEEE 754 is the international standard that defines exactly how computers store floating point numbers. A 64-bit double uses 64 bits total: 1 for the sign, 11 for the exponent, and 52 for the fractional part (mantissa). The mantissa is where the infinite binary expansion gets cut.

The real value of 0.1 in binary is 0.000110011001100110011... repeating forever. IEEE 754 cuts it after 23 bits (32-bit) or 52 bits (64-bit). The stored value is not exactly 0.1 — it is the closest number that fits.

So what does the computer actually store?
When you write 0.1 in your code, the computer stores the nearest representable 64-bit value. That value is not exactly 0.1. It is slightly more. You can see the full value if you ask for enough decimal places.
what you write: 0.1
what is stored: 0.1000000000000000055511151231257827021181583404541015625
what you write: 0.2
what is stored: 0.200000000000000011102230246251565404236316680908203125
Both are off by a tiny amount. When you add two approximations together, the errors add too.
4 / 5
0.1 + 0.2 — what actually happens.
The computer does not add 0.1 and 0.2. It adds the two approximations it stored. Then it rounds the result to the nearest representable value. The final answer carries all three errors.
0.1000000000000000055... (stored 0.1)
+ 0.2000000000000000111... (stored 0.2)
= 0.30000000000000004 (after rounding)
the true sum 0.3 is not representable either — so it rounds to the nearest value, which happens to be slightly above
This is not a bug. It is the correct result given the constraints. The IEEE 754 standard guarantees this is the best possible answer — the nearest representable float to the true sum. It just isn't 0.3.

Order changes which errors accumulate.
Because each intermediate result is rounded, the order you add numbers changes the sequence of roundings. Different roundings → different accumulated error → different final result. All of these are correct to the last bit. They are just not the same.
((0.1 + 0.2) + 0.3) + 0.4   ← left to right
0.9999999999999999
3 roundings, errors stack upward
(0.1 + 0.2) + (0.3 + 0.4)   ← parallel pairs
1.0
errors happen to cancel
0.4 + 0.3 + 0.2 + 0.1   ← right to left
1.0
different rounding sequence, same luck
0.1 + 0.4 + 0.2 + 0.3   ← random shuffle
0.9999999999999999
same total, different path, different error
This is why the same model trained on a GPU gives a slightly different loss than on a CPU. The hardware runs the additions in a different order. Each result is correct — they are just not identical to each other.
